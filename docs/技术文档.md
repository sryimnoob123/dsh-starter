# dsh-starter 技术文档

> 本文件是 dsh-starter 的**详细技术文档**，面向开发者和需要理解内部机制的人。
> 面向使用者的简介见根目录 `README.md`。版本基线：**v0.4.1**。

---

## 1. 项目定位

`dsh-starter` 是 DeepSeek Harness（DSH）的桌面客户端——一个**极薄**的 Electron 壳：

- **不重写 DSH**：自己拉起本机的 `dsh` 服务，把官方 Web 界面装进无边框原生窗口。
- 壳只负责四件事：**窗口、托盘、通知、服务生命周期**；其余（界面、功能、agent 能力）全在 DSH 侧。
- **managed 模式**（唯一模式）：壳**拥有并启动自己的 DSH 服务**，不复用外部已装的服务。

## 2. 架构总览

```
┌─────────────────────────────────────────────────────────┐
│  Electron 主进程（src/main）                              │
│  ├─ app.ts           启动序列 + 服务生命周期 + 窗口/托盘    │
│  ├─ service/         spawn、端口探测、rpc、watchdog        │
│  ├─ install/         dsh 安装 + win32 插件自动装           │
│  ├─ onboarding/      首启向导（API 接入）                  │
│  ├─ prompt/          提示词/身份/persona 注入              │
│  ├─ window/          无边框外观、拖拽条、设置扩展注入        │
│  ├─ runtime/         Node 运行时自动补齐                   │
│  ├─ updater/         electron-updater 自动更新             │
│  ├─ bridge/          渲染进程 ↔ 主进程 IPC 桥（dshShell）  │
│  └─ config/logging/notify/usage/watchdog 等基础设施        │
└──────────────┬──────────────────────────────────────────┘
               │ DSH_HOME=<安装目录>/dsh-home
               ▼
┌─────────────────────────────────────────────────────────┐
│  DSH 服务（<安装目录>/dsh/node_modules/@deepseek-ai/dsh）  │
│  · 打包时打进安装包（离线），壳用 node 直跑 lib/bin.js      │
│  · 官方 Web GUI 渲染进壳窗口（http://127.0.0.1:<port>）    │
│  · 配置/凭据/会话/插件全在 dsh-home 里                     │
└─────────────────────────────────────────────────────────┘
```

**核心原则**：壳极薄、可扩展（[FR-6]）；服务端能力优先做成 DSH 侧插件，壳只做承载面。

| `bridge/` | IPC 桥（`window.dshShell` ↔ 主进程，`contextIsolation` 隔离）|

## 4. 关键机制详解

### 4.1 服务生命周期（managed 模式）

1. 启动序列（`app.whenReady` → `startShell`）：
   检测 dsh → 探测端口 → `spawn` → 等服务就绪（stdout URL 行 或 端口探测）→ 加载页面。
2. **dsh 来源**：优先内置 `<安装目录>/dsh`（打包时打入），其次 PATH 全局 dsh（此时弹窗问用哪个）。
3. **DSH_HOME**：经环境变量注入，指向 `<安装目录>/dsh-home`（壳 exe + dsh + 数据三样同目录）。
4. **崩溃自愈**：服务曾就绪后崩溃 → 指数退避重启（≤5 次）；主动停止/退出则置 `intentionalKill` 不再自愈。
5. **端口**：智能探测（默认 3080，冲突自动换空闲端口，记住用过的端口）。

### 4.2 打包 / 安装（离线）

- `scripts/prepare-dsh.mjs`：打包前 `npm install @deepseek-ai/dsh` 到 `vendor/dsh`（npmmirror）。
- `build/electron-builder.yml` 的 `extraFiles`：`vendor/dsh/node_modules` → `<安装目录>/dsh/node_modules`。
- 安装时**零联网、零 npm**，双击即用。DSH 版本**未锁定**（每次打包拉当时最新，出包前需回归测试）。

### 4.3 自动更新

- `electron-updater`：自动检查 + 自动下载，**安装由用户确认**（`quitAndInstall`）。
- 发布源 = GitHub Releases（`latest.yml` + NSIS 安装包 + blockmap）。
- **升级保护**：`build/installer.nsh` 用 `${ifNot} ${isUpdated}` 跳过删除 `dsh-home`/`dsh`，所以用户自装的插件/预设/配置**跨升级保留**；只有主动卸载才清空（`deleteAppDataOnUninstall: true` 也只删 AppData 于卸载时）。
- **NSIS 必须 `oneClick: true`**：带向导的 assisted 安装器（`oneClick:false`）在 electron-updater 静默拉起时无法无人值守走完向导、会挂起，导致自动更新装不上。v0.4.1 实测踩到（已发布的 v0.4.1 正是 assisted 包），下一版本需改用 oneClick 包重打并**实测更新能装完再发**。
- **`resources/app-update.yml` 必须存在**：electron-builder 产物会自动内嵌；但手工拷贝/精简出来的测试目录常漏它 → `checkForUpdates` 读不到发布源而**静默失败、无任何提示**。排查「点更新没反应」先确认这个文件在。
- **当前更新 UX（O1 已落地）**：独立 OpenChamber 风进度小窗（`pages/update.html` + `updater/progressWindow.ts` + `updater/update-preload.cjs`）实时显示下载进度/下载完成/失败；自动检查与手动检查都在**真正开始下载**时弹。用户 ✕/「稍后」隐藏后，托盘常驻「安装更新 vX」入口与「下载完成」通知兜底；手动检查失败也弹通知。两处防打扰：`update-not-available` 只在手动检查时提示；**已下载待装、重启后再检测到时不重复弹窗**（靠 `download-progress` 是否触发区分「新下载」与「缓存待装」）。

### 4.4 窗口外观（无边框 + 原生拖拽）

- `frame:false` + 自绘标题栏（悬浮窗口按钮：检查更新/最小化/最大化/关闭，右上角）。
- **拖拽 = 原生 `-webkit-app-region: drag` 顶部 24px 拖拽条**（`DRAG_BAR_SCRIPT`）：
  - 原生拖拽由 Windows 处理 → 无 DPI 漂移、**自带双击最大化**、正确配合缩放边与 Aero 贴靠。
  - 顶部 24px 内的 DSH 交互元素（面包屑/标签/按钮）由脚本动态标 `no-drag` 并抬到拖拽条之上，保持可点。
  - 顶部会话 header 标题行加 150px 右 padding，给悬浮按钮让位（避免与 DSH「导出/下载对话」按钮重叠）。
- **历史教训**：早期版本用 JS `setPosition` 16ms 循环拖拽，在 150% 缩放下 DIP/物理像素换算漂移 → 窗口"越拽越大"，且无双击最大化——已整体废弃，改用原生拖拽。

### 4.5 提示词 / 身份 / persona 注入

- 落点 = DSH 官方机制：
  - `$DSH_HOME/cordis.patch.yml`（home 根）——persona/身份，`watchUserPatches` 热重载。
  - `$DSH_HOME/AGENTS.md`——全局指令（所见即所注入），原子写。
- 壳只写这两个文件，且只在用户点「保存」时写（不启动时自动写）。**web profile 的 `cordis.patch.yml` 是另一个文件**（见 §4.7），壳不碰 home 根以外的 patch。

### 4.6 首启向导 / API 接入

- 向导第一步选渠道：官方 DeepSeek（`api.deepseek.com` → `llm-deepseek`，原生思考强度 off/high/max + 凭据 `DEEPSEEK_API_KEY`）/ 通用 OpenAI 兼容（`llm-pi-ai`，凭据 `DSH_DESKTOP_KEY`）/ opencode Zen（预填 baseURL）。
- 支持「获取模型列表」（`GET /v1/models`）+ 测试连接。
- 思考开关按模型能力显示（诚实派）：模型声明了 `reasoningEfforts` 才显示。

### 4.7 win32 持久终端修复（捆绑插件）

**问题**：DSH 官方 `@deepseek-ai/dsh-subprocess-local` 的 `createProcessInspector()` 只有 Linux/macOS 后端，Windows 上持久终端（`tool-bash-persistent`）一 spawn 就抛 `terminal inspection is unsupported on platform win32`。

**修复**：捆绑第三方插件 `dsh-win-terminal-inspector`（MIT，© 2026 clearkurt，**原样未改**）：
- vendor 位置：`vendor/win-terminal-inspector/`（含 LICENSE/NOTICE/源码），打包进 asar。
- 首启自动装：`src/main/install/winInspectorPlugin.ts` 在服务就绪后，把插件文件落到 `<DSH_HOME>/profiles/web/plugins/dsh-win-terminal-inspector/`，并在 **web profile 的** `cordis.patch.yml`（`profiles/web/cordis.patch.yml`）幂等追加 insert 条目。
- 装一次记一次（`shell-config.json` 的 `winTerminalInspectorInstalled`），用户手动卸载后不反复重装。
- 插件经 DSH 官方 `terminalInspector` 钩子注入，不修改任何官方 node_modules，卸载即还原。

**仍存在的边界（沙箱）**：~~默认 `workspace-write` 下 Git Bash（MSYS）建不了信号管道，持久终端会报 `PTY shell exited during startup`。~~ **已解决（O2-A 落地）**：新会话默认权限改为 **Full access**（`danger-full-access`），持久终端开箱即用。实现：壳服务就绪后经 `settings.update({ns:'permission', patch:{defaultPreset:'danger-full-access'}})` 写 DSH 官方设置（`permission.defaultPreset` 影响后续新 Web 会话，已开会话不变）；按 `shell-config.json` 的 `permissionDefaultApplied` **只写一次**，之后用户手改（回 workspace-write 等）壳不覆盖。代价仍是：Full access 下命令不受文件沙箱约束。

> 只列**已确认可复现/可论证**的项；每项标类型（bug / 优化）与状态。改动仍按需求文档 §2 走变更三步。

### 7.1 已知 bug

| # | 类型 | 问题 | 现象 | 状态 |
|---|---|---|---|---|
| B1 | bug | 自动更新安装器挂起 | 已发布的 v0.4.1 用 assisted 安装器（`oneClick:false`），electron-updater 拉起后挂起、装不上 | `oneClick:true` 已改；下版本重打 + **实测装完再发**（本次待办） |

| B3 | bug | Windows 持久终端需 Full access | `workspace-write` 下 Git Bash（MSYS）建不了信号管道，报 `PTY shell exited during startup` | **已修（O2-A）**：新会话默认 Full access，开箱即用；改动见 §4.7 |

| # | 优化 | 说明 |
|---|---|---|
| O1 | 更新 UX 补全 | **已落地**：独立进度小窗（发现/进度/完成/失败全可见，自动+手动都弹）+ 托盘「安装更新 vX」常驻入口 + 手动检查失败通知。见 §4.3 |
